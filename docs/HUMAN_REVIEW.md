# AI Chargeback Guardian — Human-in-the-Loop Review System (Step 6)

## Overview

The **Human-in-the-Loop (HITL) Review System** is the decision and governance gate of the AI Chargeback Guardian. It ensures that automated AI responses and machine learning predictions remain strictly advisory drafts until an authorized human analyst reviews, edits, and formally approves or rejects the case.

---

## 1. Review Workflow State Machine

```
              +---------------------------+
              |     AI DRAFT CREATION     |
              +---------------------------+
                            |
                            v
              +---------------------------+
              |      PENDING_REVIEW       |
              +---------------------------+
                            |
         +------------------+-------------------+------------------+
         |                  |                   |                  |
         v                  v                   v                  v
+------------------+ +------------------+ +-----------------+ +-----------------------+
|     APPROVE      | | EDIT_AND_APPROVE | |     REJECT      | |  NEEDS_MORE_EVIDENCE  |
+------------------+ +------------------+ +-----------------+ +-----------------------+
         |                  |                   |                  |
         v                  v                   v                  v
+------------------+ +------------------+ +-----------------+ +-----------------------+
|  Status: RESOLVED| | Status: RESOLVED | |  Status: CLOSED | | Status: UNDER_REVIEW  |
|  (Merchant Win)  | |  (Merchant Win)  | | (Merchant Concede)| (Investigation Paused)|
+------------------+ +------------------+ +-----------------+ +-----------------------+
```

### Review States:
- **`PENDING_REVIEW`**: Initial state upon dispute ingestion and automated AI drafting. Awaiting human analyst action.
- **`APPROVED`**: Human reviewer validated the automated AI draft without changes and authorized contest filing.
- **`EDITED_AND_APPROVED`**: Human reviewer modified the rebuttal statement (e.g. customized courier details) and authorized contest filing with the revised text.
- **`REJECTED`**: Human reviewer determined the merchant should concede the dispute (e.g. valid customer claim).
- **`NEEDS_MORE_EVIDENCE`**: Human reviewer identified evidentiary gaps and halted submission until missing documentation is retrieved.

---

## 2. Strict Approval Safeguards

The system implements automated gate checks before allowing a reviewer to authorize an approval:

### Critical Grounding Safeguard:
1. **Zero Hallucination Tolerance**: If the AI response engine's grounding status is `FAILED` (e.g. draft claims delivery was confirmed when `delivery_confirmed=False` in the database), the backend **STRICTLY PROHIBITS** `APPROVE` and `EDIT_AND_APPROVE` actions.
2. **Action Restriction**: When grounding fails, the reviewer is restricted to either `NEEDS_MORE_EVIDENCE` or `REJECT` until the evidence records are corrected.

### Field Validations:
- **`EDIT_AND_APPROVE`**: Requires an `edited_response` string with at least 10 characters.
- **`NEEDS_MORE_EVIDENCE`**: Requires mandatory `reviewer_notes` explaining which specific documentation or courier proof is missing.

---

## 3. Human Review Persistence & Schema

Every decision is recorded in the `human_reviews` relational table:

| Field | Type | Description |
| :--- | :--- | :--- |
| `id` | `INTEGER PK` | Unique review event ID |
| `dispute_id` | `INTEGER FK` | Reference to `disputes.id` |
| `reviewer_reference` | `VARCHAR(50)` | Synthetic reviewer identifier (e.g. `REV-00892`) |
| `original_ai_recommendation` | `VARCHAR(50)` | Advisory recommendation from AI (`CONTEST`, `REVIEW`, `ACCEPT`) |
| `original_ai_response` | `TEXT` | Exact text generated by the AI engine |
| `reviewer_decision` | `VARCHAR(50)` | `APPROVE`, `REJECT`, `EDIT_AND_APPROVE`, `NEEDS_MORE_EVIDENCE` |
| `edited_response` | `TEXT` | Custom modified rebuttal statement (if edited) |
| `reviewer_notes` | `TEXT` | Analyst commentary and audit observations |
| `reviewed_at` | `DATETIME` | Timestamp of reviewer action |

---

## 4. Immutable Audit Trail Integration

Every human review action triggers an immutable audit log entry in the `audit_logs` table:
- `REVIEW_APPROVED` (actor: `HUMAN`)
- `RESPONSE_EDITED` (actor: `HUMAN`)
- `REVIEW_REJECTED` (actor: `HUMAN`)
- `MORE_EVIDENCE_REQUESTED` (actor: `HUMAN`)

---

## 5. Security & Synthetic Isolation

- **Synthetic Identifiers**: All reviewer references are synthetic (`REV-00892`, `REV-00145`) with no real employee PII.
- **Prototype Boundary**: Authorizing a dispute does **not** trigger real financial transactions or live card scheme network calls.
- **Input Sanitization**: Reviewer notes and custom rebuttal drafts are sanitized against script injection and command escapes.
